# Compile-time attributes — quick introduction

TypePHP reads these attributes **at compile time** and expands them into ordinary methods. No
reflection, no runtime metadata, no dynamic dispatch. A method generated by `#[Getter]` is
indistinguishable from one you typed by hand.

This file is the orientation. The full reference — every attribute, exact syntax, composition
rules, and the real diagnostics — is `attributes-reference.md`.

## The one paragraph that matters

All built-in attributes live in the **root namespace**. Inside `namespace App;`, writing
`#[Getter]` resolves to `App\Getter`, and the compiler treats it as an unknown attribute: **silently
ignored, no error, no generated method**. You find out when `getName()` does not exist. Write
`#[\Getter]` or `use \Getter;`.

This is the first mistake everyone makes and it is invisible in `--dry` output.

## A working example

Verified end-to-end (compiled, linked, ran):

```php
use \Getter;
use \Constructor;
use \MethodsFor;

final class User
{
    #[Constructor, Getter]
    private int $id;

    #[Constructor, Getter]
    private string $name = '';
}

#[MethodsFor(\Type::String)]
final class StringExtensions
{
    public static function greet(string $name): string { return 'hi ' . $name; }
}

function main(): void
{
    $u = new User(7, 'rango');
    echo $u->getId(), ' ', $u->getName(), "\n";   // 7 rango
    echo 'rango'->greet(), "\n";                  // hi rango
}
```

## What exists

| Family | Attributes |
|---|---|
| generated methods on properties | `#[Getter]` `#[Setter]` `#[With]` `#[Constructor]` |
| generated methods on classes | `#[Printer]` `#[Arrayable]` |
| extension methods | `#[MethodsFor(Type::String)]` `#[MethodsFor('*')]` `#[MethodsFor(SomeClass::class)]` |
| parameter contracts | `#[NotNull]` `#[NotEmpty]` `#[Validate(FILTER_VALIDATE_*)]` |
| compiler contracts | `#[Immutable]` `#[MustUse]` `#[Override]` `#[NoExport]` |
| codegen hints | `#[Hot]` `#[Cold]` |

## What costs nothing and what does not

"Compile-time attribute" sounds free, but only the *expansion* is free:

| Zero runtime cost | Real runtime cost |
|---|---|
| the attribute machinery itself | `#[With]` — clone plus assignment |
| `#[Immutable]` — pure static check | `#[Printer]` — property reads, string joining |
| `#[Override]`, `#[MustUse]`, `#[NoExport]` | `#[Arrayable]` — building the array |
| `#[Getter]` / `#[Setter]` / `#[Constructor]` — plain methods | `#[NotNull]` / `#[NotEmpty]` / `#[Validate]` — one check branch per call |
| `#[Hot]` / `#[Cold]` — compiler attributes | — |

## `#[Immutable]` versus `readonly`

Both prevent mutation, but `readonly` is a *runtime* feature: the compiler cannot optimize property
access through it and inserts object-level hooks. The docs describe dense access through `readonly`
as **an order of magnitude slower** than a plain property.

Preferred shape:

```php
class Config
{
    #[Getter]
    private int $port;          // private + Getter instead of readonly public

    public function total(int $n): int
    {
        $t = 0;
        for ($i = 0; $i < $n; $i++) {
            $t += $this->port;  // class-internal access, not getPort()
        }
        return $t;
    }
}
```

Same reasoning for property hooks: inside the class, read the backing field; leave the hook for the
public interface. Rewriting a hook as a normal method changes nothing — the cost difference is
*property access* versus *method call*, not hook versus method.

## When to reach for these

Use them when the boilerplate is repetitious and mechanical: DTOs, value objects, helper
namespaces. Do not reach for `#[Native]` or `#[Hot]` speculatively — both trade something away
(reflection/framework interop; code size) for performance you have not measured.

For everything else — `#[Printer]`, `#[Arrayable]`, `#[Validate]` options, provider method rules,
`#[MustUse]` scope, `#[Override]` edge cases — see `attributes-reference.md`.
